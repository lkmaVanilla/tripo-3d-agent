## Context

动机与范围见 [proposal.md](proposal.md)。行为要求分别见 [agent-audience](specs/agent-audience/spec.md) 和 [verified-results](specs/verified-results/spec.md)。实现基线为 `49a1364`；以下均为设计，不代表已经实现。

当前与本变更直接相关的事实：

| 位置 | 当前行为 | 对设计的约束 |
|---|---|---|
| `internal/app/agent.go`、`skills/intent.md` | 系统身份限定游戏开发者，需求 Skill 预设游戏原型用途；其他 Skill 主要描述静态制作与技术纠偏 | 修正有冲突的受众表达，保留仍然正确的静态阶段规则 |
| `agent.go` 的 `finish_request` | `deliver/artifact_id/explanation`；核对产物通过后把解释原文写入 `Final`，失败分支同样写入原文 | 缺口在正式事实来源，无需增加生产能力或必填工具参数 |
| `types.go`、`asset/check.go` | `Session` 保存终态、候选与报告；报告已区分有效、通过、无法验证和视觉边界 | 重用已有事实，不增加新的技术检查类别 |
| `service.go`、`production.go` | Agent 结束、停止、到期、错误收尾和恢复分别调用 `Finish` | 必须统一收尾依据，避免只修模型成功分支 |
| `http.go`、`Session.View()` | 普通请求、WebSocket 与导出复用公开视图；模型也读取该视图作为运行状态 | 保留 `session.final` 字符串和现有状态枚举，集中构建公开结果 |
| `recovery_seed.go`、`agent.go` | 种子直接匹配全局 PromptVersion；重建输入必须逐字节匹配输入哈希 | 只改常量或放宽版本白名单都不足以兼容旧暂停 |
| `skillBackend` | 所有会话读取当前嵌入 Skill，哈希只记录加载版本 | 需要有限的版本选择，才能冻结旧会话的后续加载内容 |

当前主规格 `checkpoint-recovery` 的事务、身份、原提议重建和停止优先要求继续有效。本设计不改 Eino 私有检查点格式、不升级 Eino 或供应商协议。

## Goals / Non-Goals

**Goals:**

- 对齐新会话中的受众定义，并保证在途旧会话继续按其原提示和 Skill 解释原协议。
- 正式结果只输出程序有依据的事实；模型原始解释保持可追踪、可独立评测。
- 正常、失败、停止、恢复与历史数据的输出使用共同规则，现有前端直接兼容。

**Non-Goals:**

- 不编辑 `internal/web/`，不调整静态页面文案、样式或交互；不重构 WebSocket 投递方式。
- 不实现自由文本通用真伪判断，不用第二个模型审查第一个模型，也不以正则扫描任意自然语言承诺完整事实核查。
- 不拆分 Session/Run/Asset，不引入资产版本树、动态 Skill 注册或通用提示管理平台。
- 不自动修正第一次意图提取错误、不增加视觉验收、不改变生产或预算策略。

## Decisions

### 1. 受众修正只作用于模型指引，明确当前制作范围

新系统提示将身份表达为面向 3D 创作者的资产制作助手；当前能力仍明确为文本到单个静态、自包含 GLB，以及既有技术纠偏。需求 Skill 将“游戏原型用途”改为“用户实际用途”，说明不能无依据地补成游戏场景。

核对三份 Skill、Skill 目录说明、Agent 描述及模型可见的输入描述：仅调整与服务对象、阶段范围或正式结果规则冲突的内容。生成与纠偏 Skill 中的静态支持条件、默认值、约束和预算保留；游戏木箱仍可作为有效案例。

采用此方案而非只修改 Skill，是因为系统身份若仍限定游戏开发者，会继续与新 Skill 互相冲突。也不把“3D 创作者”扩写为任意 3D 操作授权。

### 2. 按会话选择两个内置执行配置

为 `Session` 增加可选的执行配置版本标识。首轮只维护固定的 `asset-agent-v1` 和 `asset-agent-v2` 两个内置配置：

- v1 冻结当前系统指令、Agent 描述、模型可见工具描述与参数 schema、Skill 名称/目录说明/正文及逻辑路径。
- v2 包含受众与正式结果规则的修正；新建会话明确保存 v2。
- 当前基线的历史会话缺少字段时按 v1 解析；如果已存种子或版本事件与该推定矛盾，不能静默覆盖，按恢复身份异常处理。
- Runner、Skill backend、模型调用事件、种子创建和校验均读取会话选择的配置。配置解析必须在所有 Runner 创建前完成，涵盖没有 `PendingPause.Seed` 的普通 Resume 和 `legacyPending`，不能只在种子校验时选择版本。旧会话恢复及后续正常模型调用保持 v1，直至原请求结束。
- 恢复协议版本与提示配置版本分别维护；本变更不因新增提示字段就重置恢复代次或修改原始 checkpoint 字节。

保留输入、响应、工具调用 ID、参数及推理字段的完整校验，并检查种子配置与会话一致。未知版本仍拒绝；已知任务和未知提交继续按既定规则处理。不能通过重算摘要、重写种子版本或重新问模型来“兼容”。

替代方案是所有旧会话立即切 v2，但 `recoveryInput` 会删除旧 system 后由 Runner 重建前缀，随后输入哈希不匹配；仅增加版本白名单也无法解决。因此选择按会话冻结，代价是暂时保留一份旧指引。旧配置只服务原请求，不能成为新会话默认值。

结果可信度由新的 Go 规则统一约束 v1/v2；保留旧模型指引不意味着继续接受其自由文字作为正式事实。

### 3. 保留工具输入，增加小型终态依据

`finish_request` 继续接受 `deliver`、`artifact_id`、`explanation`，不增加必填字段；模型仍负责选择动作并给出原始理由。

会话增加可选、版本化的终态依据（拟命名 `Result`），只保存生成正式结果所需的最少信息：规则版本、结果状态、结束来源、程序原因代码、相关资产/操作引用，以及证据是否充分。终态、时间和预算仍以 Session 原有事实为准，技术数据仍以 `Artifact.Report` 为准，不另建可被模型填写的面数或体积副本。

正常交付必须在本请求中找到选中资产，并核对既定技术检查确实通过。完整通过证据包括可关联的本请求资产/任务、报告的有效和通过标志、正数实测值及上限、数值未超限，以及文件有效性/几何规模/文件体积三项通过记录；不能只读取一个 `Passed=true`。程序从对应报告生成 `Final`，描述实测值、验收上限、检查项和未检查的外观范围。报告无法解析时，不读缺省零面数作为可信测量。

`deliver=false` 只提供“Agent 选择结束”的来源。程序可以同时描述已有候选、检查结果和实际额度，但不会将 explanation 中的“预算已用完”“全部方案不可行”“用户硬约束冲突”认证为事实；即使存在合格候选，也要区分“已有候选”和“已选择交付”。

这比增加结构化理由枚举后要求模型填准更小，也避免改变旧工具协议。模型解释的语义正确性继续由独立评测检查。

### 4. 统一所有终止路径，生成结论不产生副作用

在现有 `Store.Edit` 事务内，以最新 Session 和类型明确的结束来源构造终态依据与 `Final`，同时保存选中引用及对应结束事件。保留 `Ended`、`Expires`、名额释放和终态幂等规则，不在事务中调用模型、供应商或重新读取模型文件。

| 入口或状态 | 正式结果允许陈述的事实 |
|---|---|
| Agent 交付 | 所选本请求资产及报告支持的技术通过；原始解释单独保存 |
| Agent 不交付 | Agent 已结束请求、没有作出交付选择，以及已有检查/额度事实 |
| 用户停止、生产期限或空闲期限到期 | 本地执行结束及具体来源；没有取消证据时不宣称远端取消 |
| `submitting` 且无 TaskID | 无法确认提交结果，保留已扣额度，不推导远端失败 |
| 模型额度耗尽 | 按原策略查询已知任务或交付已有合格资产；没有合格证据不能交付 |
| 原任务确定性恢复 | 原 TaskID、原报告及恢复收尾来源，不宣称发生了新决策或新生产 |
| 操作、模型或恢复错误 | 由程序识别的失败阶段与代码；原始外部错误正文只保留为来源证据 |

改动覆盖 `finish_request`、`Service.Stop`、调度到期收尾、`finalize`、`recoverKnownTask` 及启动恢复通过它们触发的结束。程序原因由类型明确的触发条件、持久状态或已有错误代码得到；未知错误统一表达为阶段失败，不从自由文本推断更具体的业务结论。

晚到回调先核对最新终态，不覆盖用户停止或到期；事务失败不对外发布新结果。沿用现有事件身份和事务边界，重复调用只保留既有终态效果，不引入另一套终态状态机。

### 5. 正式结果投影兼容现有网页，原始提议仍可评测

集中生成公开结果供 `Session.View()`、`snapshot`、WebSocket 和导出使用。保留 `final` 字符串、当前状态枚举和已有产物结构；可增加结果版本、来源、引用及证据状态字段。前端继续使用原 `app.js` 和 `index.html`，无需新组件。

原始模型提议及 explanation 不拼进 `Final`。既有 `agent_proposal`、`agent_finished` 等记录保留原始内容并明确来源/未核验属性；外部错误细节同样与程序原因分开，继续沿用脱敏和匿名归属校验。不要删除、替换历史事件或泄露 History、checkpoint、密钥及访问凭证。

单次核验增加正式结果与报告/状态的证据一致性检查；原始自由解释的语义正确性标为 `unverifiable`，不因程序结果正确就标为通过。现有前端已经能展示此检查状态，无需修改固定文案。结构化交付引用被拒绝仍记录 `false_validation` 等违规证据；不声称程序能自动发现自由解释中的全部谎言。

### 6. 历史终态只重建能够证明的事实

不批量重写已结束会话的原始 `Final`、事件和时间字段。仅对 `Terminal()` 为真且没有新结果版本的历史会话，在读取时生成只读结果投影；在途会话的 `runtime_state` 和恢复判断不经过历史终态降级：

- 交付引用和报告完整、相互一致时，公开 `final` 从报告重新生成，结果来源标为历史证据推导；不补写“当时已运行新版验证”的事件。
- 历史 `completed` 缺少交付证据时，公开视图使用现有 `failed` 值表达“已结束”，`final` 明确说明历史证据不足，公开交付选择为空；原始状态和说明放在带来源的历史审计字段中。数据库里的原始状态和 `Ended/Expires` 不变，该投影不参与调度或恢复。
- 逐个核对候选报告。证据不完整或矛盾的报告保留公开字段形状，但将无法支持的检查项标为 `unverifiable`，不透传无依据的 `passed=true` 或检查明细；有效性不能证明时也不宣告文件有效。原始报告保留为带来源的历史审计信息。交付引用缺失不等于所有候选无效，另一个有完整技术证据的候选仍可正确显示其自身检查结果。
- 其他旧终态只根据结构化状态确认“已结束/已停止”等事实，不从旧自由说明猜测具体原因；原始说明作为未核验历史证据保留于脱敏导出。
- 普通快照、WebSocket、导出和单次核验共用该投影，避免正文说证据不足而状态徽标或无据候选仍显示技术通过。现有页面会自动选择最新候选，因此候选报告投影与主结论投影必须一并验证。

采用读取时投影而非重跑或批量改写，既保证正式输出的事实边界，也保留历史证据和现有清理规则。此路径不调用模型、供应商或新技术检查。

### 7. 验证分别证明程序保证与模型行为

- 用固定模型提议和本地报告验证伪造面数/绑定、无效交付、停止理由、未知提交、无法验证、预算和恢复收尾；检查结果来源与状态关系，不只比较固定模板文字。
- 在真实 Eino 中构建冻结 v1 的暂停、草案及旧工具参数，再切换默认 v2 的应用恢复。夹具不能引用“当前最新 instruction/Skill”而冒充旧版数据。
- 对比终态普通接口、WebSocket 和导出，覆盖旧数据投影、访问隔离、脱敏、停止并发及写入失败；检查 `internal/web/` 无差异，不为简单文案写镜像断言。
- 准备 4 个定向案例：产品展示静态资产、游戏原型静态资产、要求未接入绑定/动画、超限结果后的解释。每例使用真实 LLM 与固定 Tripo 测试响应运行一次，保留全部提议、Skill 版本和结果，核对受众偏置、能力承诺及解释。它们只提供本变更的小样本行为证据，不形成新的通过率门槛或替代完整 60 次评测；受控样本注入的错误解释也不能算真实模型犯错证据。
- 执行相关恢复回归与全量 `go test -race ./... -count=1`、`go vet ./...`；真实 LLM 调用与纯受控测试分开记录。若真实模型暂不可用，明确该验证未完成，不能把任务标为通过。

## Risks / Trade-offs

- [旧会话仍使用旧受众指引] → 只持续到原请求结束，新会话使用 v2；正式结果的可信规则统一升级，后续是否移除 v1 应依据旧数据保留情况单独决定。
- [改了版本但历史前缀未冻结] → 冻结 v1 的消息相关配置和 Skill，保留严格哈希校验，并用真实旧版夹具验证；不能通过跳过校验通过测试。
- [正式结论更受约束，模型的自由表达减少] → 原始决策理由仍保留在执行记录用于理解与评测；不把它混入已核验的事实。
- [旧完成状态的公开投影变保守] → 原始状态和说明仍可审计，投影明确证据不足；不修改数据库终态、期限或后台行为。
- [遗漏某个收尾路径] → 以现有所有 `Finish` 调用点建立回归矩阵，正常与恢复共用事实构造，并测试停止后的迟到结果。
- [小样本模型检查无法证明普遍正确] → 只报告实际运行结果，原完整 Agent 评测状态保持独立，不宣称解决所有意图或解释错误。

## Migration Plan

1. 实施前冻结当前 v1 配置及升级夹具；新增可选会话字段和结果依据，不改变 SQLite 表的 checkpoint 内容、代次或摘要。
2. 更新程序同时支持 v1/v2。旧缺字段会话按已知 v1 基线解析并核对已有版本证据，新会话保存 v2；终态历史读取使用只读投影。
3. 在临时数据副本上完成旧澄清、草案、已知任务、未知提交、旧结束记录及重复启动回归。生产部署按既有单服务方式停止旧进程并备份数据库与模型目录。
4. 仅在尚未接纳新动作或推进旧请求的升级阶段，才能恢复备份并回到旧程序。一旦写入 v2 会话或执行推进，不直接运行不认识 v2 的旧二进制，也不恢复可能丢失任务 ID 或用户答案的旧快照；保留当前数据前滚修复。

本设计没有需要在实施阶段再决定的产品范围问题。辅助函数名称和字段具体组织可以在遵守上述输出与兼容要求的前提下调整。
