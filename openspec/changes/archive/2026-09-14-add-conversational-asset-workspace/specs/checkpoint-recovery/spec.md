## MODIFIED Requirements

### Requirement: 恢复点身份一致

Runtime MUST 核对恢复点与其所属单次执行、该执行的会话归属、逻辑暂停及递增代次的绑定关系和完整性；旧代次、其他执行、其他会话或内容不匹配的恢复点不得推进当前动作。同一会话中新目标的执行 SHALL 使用独立恢复身份，不能复用旧目标的暂停或恢复状态。旧记录原有恢复身份仍代表原单次执行，兼容处理不得改写恢复字节来冒充另一执行。对同一次提交的重复确认不得重复产生业务效果。

#### Scenario: 第二轮暂停覆盖第一轮
- **WHEN** 第二轮澄清已经生效，旧执行实例尝试使用第一轮的恢复点或提交结果推进请求
- **THEN** 系统拒绝该旧结果，第二轮问题、答案、额度和恢复点保持不变

#### Scenario: 跨会话恢复点混用
- **WHEN** 一个请求被提供另一个会话的恢复点或暂停身份
- **THEN** Runtime 在模型决策或外部副作用之前拒绝恢复，不泄露或修改另一会话的数据

#### Scenario: 提交确认重复到达
- **WHEN** 同一暂停提交的确认被重复处理
- **THEN** 仅存在一次有效暂停、一次相应澄清计数或入队效果，原提交结果可以被识别为已经完成

#### Scenario: 同会话不同执行的恢复点混用
- **WHEN** 同一会话已创建后续执行，但恢复入口收到前一次执行的暂停身份或检查点
- **THEN** 系统拒绝用它推进后续执行，不借助相同会话归属绕过执行隔离，原执行的结果、预算和恢复记录保持不变

### Requirement: 已接受答案可重放

系统 MUST 将已经接受的用户答案持久绑定到对应执行及其逻辑问题，并在该问题仍可能被恢复时保留答案。Runtime 重放同一澄清工具时 SHALL 返回原答案，不要求用户重复输入、不重复增加澄清轮数，也不得将上一问题或另一执行的答案交给当前问题。回答当前澄清 SHALL 继续原执行，不能被当作另一个制作目标而创建新预算。

#### Scenario: 接受答案后退出
- **WHEN** 答案已被系统接受并持久化，Agent 尚未获得该答案时进程退出
- **THEN** 恢复后 Agent 收到对应问题的原答案，原请求及已确认约束保持不变

#### Scenario: 工具返回答案后退出
- **WHEN** 澄清工具已经返回答案，但后继恢复点尚未提交时进程退出
- **THEN** 再次恢复同一等待点仍返回相同答案，不重复提问、不重复扣减澄清额度

#### Scenario: 多轮答案分别恢复
- **WHEN** 一个请求先后接受多个问题的答案并在后续澄清附近退出
- **THEN** 每个问题仅能读取绑定于自身的答案，恢复不改变已发生的澄清轮数

#### Scenario: 旧问题答案迟到
- **WHEN** 用户或断线客户端向当前会话提交已经结束的旧执行或旧问题的答案
- **THEN** 系统拒绝将其用于当前问题，不重开旧执行，不创建新制作目标，当前执行的答案和额度保持不变

### Requirement: 生产恢复沿用原操作

Runtime MUST 在生产准备、排队、提交、任务查询和结果返回的恢复过程中沿用原执行、操作身份、已消耗额度和截止时间。已经提交或完成的动作不得因工具重放再次提交或重复保存产物及模型版本；已知任务的确定性查询与检查继续遵守现有执行期限，未知提交继续遵守不自动重发规则。对历史版本加工的新执行 SHALL 固定真实输入版本及文件身份；供应商临时文件引用的准备与更新不得改变已接受的语义输入，也不得改写已经进入提交阶段的生产参数来触发重发。

#### Scenario: 队列暂停附近退出
- **WHEN** 一个生产暂停在入队前或入队后发生退出
- **THEN** 待提交暂停最多入队一次，已入队请求保留原顺序；不会重复占用生产名额，也不会在排队时扣生产额度或启动生产计时

#### Scenario: 队列满后恢复
- **WHEN** 请求因队列已满等待用户重试时服务重启
- **THEN** 需求与原待执行操作仍被保留，只有成功重试入队后才参与调度，不能因重建检查点自行入队

#### Scenario: 已知任务重启
- **WHEN** 请求已有持久化远端任务 ID，且未终止或到期
- **THEN** 系统继续查询该任务并检查产物，远端提交次数不增加；即使模型额度耗尽，仍在原期限内完成确定性处理

#### Scenario: 外部接收结果未知
- **WHEN** 远端可能接收了提交，但系统无法确认任务 ID
- **THEN** 系统保留该次已消耗生产额度和未知提交记录，停止自动执行，不因恢复、重新打开会话或创建后续执行而自动重新提交原操作

#### Scenario: 完成操作的结果被再次读取
- **WHEN** 已保存操作结果和产物后、后继检查点提交前退出
- **THEN** 恢复返回同一操作的实际结果，仅存在一份对应产物和模型版本记录；报告及版本来源不变，展示的剩余额度从该执行的当前持久事实计算

#### Scenario: 临时输入准备期间退出
- **WHEN** 指定版本的文件身份已固定，但内部文件上传或临时输入准备尚未完成时进程退出，且生产尚未进入提交阶段
- **THEN** 恢复只针对同一已保存文件执行有界输入准备，保留原执行期限和生产阶段，不替换为另一个版本，不把上传成功当作生产任务成功或新模型版本

#### Scenario: 提交阶段不能刷新参数重发
- **WHEN** 生产已进入提交阶段，而进程退出或响应异常使任务 ID 尚未可确认，即使原临时文件引用已失效
- **THEN** 系统保留原实际提交参数、输入版本和未知结果证据，不通过刷新文件引用、重新上传或新建执行自动重发该生产操作

### Requirement: 终止和执行边界优先

Runtime MUST 在暂停提交、恢复、领取生产名额及实际副作用之前重新核对所属执行的持久化终止状态与适用执行限制。恢复点不得覆盖更晚的停止、超时、预算或用户操作时间；历史额度和绝对截止时间不得因恢复而重置。会话仍可交互不表示旧执行仍可恢复；用户停止 SHALL 只结束指定的当前执行，新目标不得复活它或继承其未完成副作用作为可重发动作。

#### Scenario: 停止与检查点提交并发
- **WHEN** 用户停止请求后，较早启动的检查点写入或恢复结果到达
- **THEN** 请求保持停止，不重新显示可继续的等待状态、不领取名额、不新增生产，保留原执行证据

#### Scenario: 恢复时已经到期
- **WHEN** 启动对账发现请求已超过生产期限或适用的生产前空闲期限
- **THEN** 系统按原规则结束请求，不重建暂停、不推进模型或生产，也不因重启延长该执行的原期限或已确定的数据保留计时

#### Scenario: 停止后继续会话
- **WHEN** 用户停止一项执行后正式发送新的要求
- **THEN** 系统按会话接受规则创建独立执行，旧执行继续保持停止，不恢复旧检查点、不取回旧远端任务或重复旧提交；旧回调不能覆盖新执行的活动状态

### Requirement: 旧记录兼容恢复

系统 SHALL 保留升级前的会话、归属、预算、任务 ID、报告及文件，并对旧恢复记录进行可重复执行的兼容处理。能够证明匹配的旧恢复点 SHALL 迁移后继续；无法证明匹配的旧记录 MUST 明确失败，禁止猜测重放或重置请求。已知远端任务即使缺少可用 Agent 检查点，仍 SHALL 在未终止、未到期时按原约束完成确定性查询与检查。建立持续会话与单次执行的关联时，系统 MUST 保留原执行身份、恢复协议内容、历史事件、结果、终止及到期时间；迁移本身不延长保留期、不重做生产，也不推断证据不足的历史版本父关系。

#### Scenario: 旧检查点存在但旧确认标志未更新
- **WHEN** 旧会话的检查点与等待身份可验证匹配，但确认标志未保存
- **THEN** 系统不因该标志拒绝恢复，迁移后可以接受原问题的回答或保留原队列位置

#### Scenario: 旧答案已经被不可逆清除
- **WHEN** 旧检查点需要一个答案，但会话和已保存消息中均没有可验证的对应答案
- **THEN** 系统明确记录无法恢复该等待点，保留现有记录，不编造答案或要求模型猜测

#### Scenario: 旧任务已知但检查点不可用
- **WHEN** 旧请求已知远端任务 ID，但 Agent 恢复点缺失或无法验证
- **THEN** Go 执行层在原期限内完成原任务查询及技术检查，按既定交付证据生成程序说明；不为修复 Agent 状态重新生成模型

#### Scenario: 重复启动迁移
- **WHEN** 服务在旧记录迁移过程中退出后再次启动
- **THEN** 迁移不会重复增加计数、产生重复会话或版本映射、重复入队或删除已有模型，已迁移记录可直接使用

#### Scenario: 已结束旧请求成为持续会话的历史执行
- **WHEN** 服务为已结束旧请求建立会话关联和历史版本索引
- **THEN** 原执行的终态、结果、报告、恢复内容及原到期时间保持不变，查看和迁移不续期，不把旧请求重新加入执行调度；用户正式继续时另按会话生命周期规则处理

#### Scenario: 历史版本来源无法证明
- **WHEN** 旧请求有多个真实产物，但现存证据不能证明某产物实际使用了哪个父版本
- **THEN** 系统保留产物与可验证的执行及操作来源，明确父关系未知，不按产物排列顺序补造加工链

## ADDED Requirements

### Requirement: 会话执行关联与版本登记可恢复

系统 MUST 在接受新消息、结束执行以及保存制作结果的持久化边界保持会话、执行、产物版本与事件一致，进程退出不得造成同一用户消息产生多个执行、同会话多个活动执行或同一生产操作产生多个版本。已经持久化的执行和产物 SHALL 可被重新识别；缺乏有效文件或可信归属的记录不得被恢复成可交付版本。清理 SHALL 尊重仍有效会话对历史执行和版本的引用，不能因首个执行原到期时间已过而删除仍在该会话有效保留范围内的文件。

#### Scenario: 消息接受后响应前退出
- **WHEN** 用户消息及新执行已经持久化，但 HTTP 响应发出前进程退出，客户端随后重试相同消息
- **THEN** 系统返回并继续原执行，不追加第二条用户消息、不新建执行或重复取得一份预算，会话活动执行唯一

#### Scenario: 文件落盘与版本提交之间退出
- **WHEN** 模型文件已经写入，但产物、版本来源与完成事件的共同保存尚未完成时进程退出
- **THEN** 恢复沿用原执行、操作和任务取得或核对同一结果，最多登记一个版本；不会出现展示成功却缺少对应版本证据，或版本指向另一执行文件的情况

#### Scenario: 执行结束后会话展示尚未刷新
- **WHEN** 执行终态已持久化，但进程在更新页面或后续读取前退出
- **THEN** 恢复展示同一正式结果，并允许按已提交结束事实判断后续消息准入，不重复结束、不永久保持虚假的忙碌状态，也不释放另一执行的活动身份

#### Scenario: 后续执行引用首个执行的旧版本
- **WHEN** 持续会话仍在有效保留期内，历史执行原有到期时间已经过去，后续执行正引用其文件
- **THEN** 系统保留有效会话所需的历史文件、版本和来源证据，不以该历史执行的独立到期值清理文件，也不通过改写其原期限伪造新的历史事实
