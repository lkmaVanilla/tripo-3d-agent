## Goals / Non-Goals

**Goals:**

- 将一次执行的可靠性保留在原边界内，并让会话和历史模型跨多次执行存续。
- 让用户、Agent 和工具对制作输入有同一个可校验的版本身份。
- 明确普通回答、制作交付、失败与停止，保持结果证据和版本来源可信。
- 通过增量包装与版本化协议兼容已有记录、网页链接和在途 checkpoint。

**Non-Goals:**

- 本次不构建通用资产平台、通用工作流引擎、多个并行 Agent 或分布式任务基础设施。
- 不引入可编辑几何历史、差异合并、版本树画布；模型版本是不可变文件与来源记录。
- 不为聊天改用双向 WebSocket 或强制增加 token 流。图片、绑定、动画及外部导入不包含在本次工具集内。

## Decisions

### D1. 增加 Conversation，保留原 Session 的单次执行语义

采用如下关系。`Run` 是本文对一次执行的统一称呼；首轮实现可保留物理 `sessions` 表及内部 `Session` 类型，避免把数据库重命名与恢复协议迁移捆绑。

```text
Anonymous visitor
  +-- Conversation
        +-- Messages
        +-- Runs
        |     +-- Intent / budget / checkpoint / outcome
        |     +-- Operations --> Tripo tasks
        +-- AssetVersions
              +-- Source run / operation / immutable file
              +-- Parent version or context reference
```

| 对象 | 持有的事实 | 不承担的职责 |
| --- | --- | --- |
| Conversation | 归属、首个资产主题、活动 Run、消息与版本索引、会话到期时间 | 不持有可覆盖所有历史执行的单一 Intent 或 Final |
| Run | 当前被接受消息、意图与约束、所选输入、模型/生产额度、期限、checkpoint、操作、正式结局 | 不因为结束而自动结束整个会话 |
| Message | 用户文字、明确的版本引用、所属 Run/问题、可展示内容及来源 | 不作为完整 Eino History 的公开副本 |
| AssetVersion | 会话、版本号、来源执行/操作、实际输入、文件摘要、格式、技术证据引用 | 不把供应商 task_id 当版本身份 |
| Operation | 一次实际生产提议、输入身份、提交与结果证据 | 不替代整个 Run 的目标与预算 |

新增 `conversations`、`conversation_runs`、`conversation_messages`、`asset_versions` 的最小持久关系。既有 `sessions/events/checkpoints` 继续保存 Run 事实。`conversation_runs` 对 `run_id` 唯一；版本以来源操作唯一登记；一个 Conversation 只允许一个非终态 Run。活跃执行指针用数据库事务维护，进程内锁仅用于调度优化；Run 已持久化停止但 worker 尚未退出时仍占据该指针，不能仅按 Run 终态开放下一个执行。

选择包装的原因是保留已有恢复身份及大量故障回归。替代方案“直接让一个 Session 重复进入 running”会覆盖原预算、Intent 和正式结果；全面重写所有存储表则增加无关迁移成本。内部类型可随后有针对性地命名整理，不要求一次全量重命名。

### D2. 每次接受的闲置态消息建立新 Run，澄清继续原 Run

```text
Conversation idle
  --> accept message + create Run
  --> understanding
       --> awaiting_answer --> resume same Run
       --> queued / queue_full --> production
       --> answer without production
  --> Run terminal --> Conversation idle
```

- 闲置态的新消息使用新 Run ID、原始消息和冻结的输入引用启动新的 Runner。不能 Resume 上一个已结束 Run 的 checkpoint。
- 同一个 Run 的澄清、首次生产、纠偏共用预算。新 Run 的上限沿用现值：最多 20 次模型调用、3 次生产提交、3 轮澄清；首次生产提交起 30 分钟；首次生产前连续 24 小时无已接受用户操作则结束。失败调用和提交结果未知仍计数，排队不提前扣生产额度。
- 纯解释或不支持能力的回答也通过这个单 Agent Run，模型调用正常计数，生产提交为零；不增加隐藏的、无预算的“聊天模型”。对会话无关的新独立资产，说明应建立新会话，不替换原资产主题。
- Run 理解中、排队、生产、收尾期间拒绝新目标，返回可识别的 `execution_busy`，不创建消息和执行，不消耗模型/生产额度。前端允许编辑草稿但禁用发送。
- `awaiting_answer` 只接受绑定该 Run、问题身份和暂停代次的回答；这是当前执行的输入，并非排队新目标。`queue_full` 仍通过原操作显式重试，不开新预算。
- 停止先持久化目标 Run 的 stopped 事实，再取消本地执行。执行协程退出前展示“正在停止”，不接受下一 Run；退出后释放匹配的活动指针。迟到 TaskID 仅可补到原操作审计，不能改变旧正式结果或新 Run。
- 停止不取消 Tripo，不取回停止后的远端结果，不恢复旧 Run。新消息不能把上一条未知提交自动变成重试；含糊的“继续/再试”应解释当前状态并澄清，明确的新制作请求才建立新的生产目标，保留原未知或停止事实。

持久化接受命令的事务顺序为：校验归属及会话有效期 → 检查消息幂等键 → 校验执行/问题/输入版本 → 保存消息与绑定 → 创建 Run 或接受原问题答案 → 写入公开事件。相同键和载荷返回同一结果，相同键不同载荷返回冲突；两个标签页发送不同新目标只接受一个。初次创建用访客范围的创建幂等键，避免响应丢失后重复新建会话和付费制作。

相比后台消息队列或执行中重新规划，该选择直接符合用户确认的交互，并使当前 checkpoint 的冻结参数边界继续成立。

### D3. 分别保存会话背景、Run Context 与 Eino checkpoint

新 Run 使用 `asset-agent-v3` 执行 profile。上下文由 Go 确定性组装：首个资产主题、当前用户原文、显式引用版本、该版本来源 Run 的意图及实测证据、最近最多 20 条可展示消息、最多 5 次已结束执行的简要结局及本次预算。最近消息正文设置总长度上限，超出时裁剪较早的自由对话并记录裁剪事实；硬约束、引用身份与所需技术证据不通过自由摘要丢弃。用户引用旧版本时，加载该版本相关事实不受最近窗口限制。

本次明确改变的要求覆盖继承要求，并在保存 Intent 前展示差异；其他约束从明确引用版本的制作背景承接。未指定版本且“这个模型”有歧义时调用澄清工具，要求用户通过版本选择器绑定输入，不能由预览焦点或“最新版本”暗中决定。最多三轮澄清仍未获得合法明确的输入时，以零生产的回答结束并说明无法确定加工对象，不能无限追问或自动创建下一 Run。一个消息最多明确引用一个模型版本；该引用、Run 初始输入和首个加工操作必须一致。后续纠偏允许使用本 Run 新产生的版本，各 Operation 单独记录其实际输入及新输出父关系，仍不得切换为其他历史版本。

差异先通过 `intent_review` 公开消息持久化为草案；同一次 `set_intent` 工具调用随后在另一事务中核对草案身份、输入和执行状态，保存正式 Intent 与 accepted_plan。草案不授权生产，崩溃后可按内容身份去重重放；不增加模型轮次或用户审批。这里的展示是可续读的先行公开记录，不要求离线用户确认已阅读。未提供的来源字段由 Go 补回，明确新值由 Agent 依据用户语义提取，程序仅如实展示字段差异，不把差异记录称为语义验证。

Intent 按 Run 冻结。本次更严格的面数上限不修改旧版本的 Report、旧 Run.Result 或 Final。输入证据与本 Run 输出分开：新增只读 `InputVersion` 和 `InputAssessment`，不把旧 Artifact 加入本 Run 的 Artifacts。若旧文件需要针对新目标检查，产生本 Run 的新 assessment，保留旧报告。

新 profile 采用版本化 `intent`、`generation`、`correction` 和后续加工指引（如 `asset-editing`）。需求指引区分回答、生成、明确的减面及不支持请求；加工指引强调目标版本和来源；纠偏仍服从本 Run 冻结目标。Go 工具门禁允许以指定历史输入开始减面，同时保留“本 Run 已有满足目标的输出时不追加生产”规则。减面失败不得未经用户明确要求改为文本重新生成；文本再生成需要明确表达其没有直接修改旧几何。

v1/v2 的指令、Skill 字节、工具 schema/description、参数解释、运行状态投影和消息协议均保留。旧 Runner 仍看到原 `runtime_state`，不会因 Conversation 增加字段而改变 ReplaySeed.InputHash。v3 的 InputVersion、assessment、目标类型使用独立投影和恢复校验。

v3 的模型边界对非空正文但没有工具、或同次响应提出多个工具的协议错误，最多再请求一次模型纠正。全部工具在验证通过前均不执行；批量调用在提供方消息副本中逐个闭合为未执行回执，保留原响应的协议字段。纠正消耗原 Run 的模型额度，每次请求重新检查停止、期限和 20 次上限；二次无效则结束为模型动作错误。空响应、接口错误及无法构造合法工具回执的响应不自动重试。纠正消息不进入 Eino 原始输入和恢复种子，重建仍只重放已经接受的响应；原始错误和纠正事件均持久保留，不因最终恢复交互而抵消评测失败。

仅用于模型的 `explanation_basis` 明确技术检查范围、视觉未验、供应商原因未诊断、参数效果不保证，以及需求/假设不等于产物事实。具体数据仍引用原版本报告、本目标输入 assessment 或本 Run 产物报告，不复制或改写这些事实。Skill 按固定目标区分合法纠偏：生成目标内的减面操作不改变目标；缺文件不证明再次生成无效；减面目标仍不能改为文本生成。该输入指引不构成自由说明的自动语义检查。

初始历史输入另投影为 `input_binding`，由持久化 `InputVersion` 确定 `not_selected/selected` 和真实版本 ID；它不是第二份选择状态。历史版本、报告和预览不构成输入授权，选中身份也不等于文件可加工或技术通过。需要初始历史输入时先澄清明确选择，再保存制作意图；用户拒绝选择则零生产回答。首次文本生成不需要历史输入，本 Run 候选的合法纠偏也不要求重新选择初始历史版本。

v3 对实际查询成功但缺少模型地址的分支持久化类型化 `missing_model_output`，普通同字面错误不获得该类型。工具反馈和后续模型上下文复用同一 `failure_evidence` 投影，绑定操作/任务身份，记录查询成功、地址缺失、文件未检查、原因未知、参数影响未排除及重试效果未知。未取得的该文件无法减面，不意味着其他已有候选不能减面；继续或结束仍服从目标、预算、期限和原工具前置条件。该投影不新增动作权限，不改变 v1/v2 反馈协议，也不将自由说明变成已验证事实。

### D4. 版本保存不可变结果，父关系表示实际加工输入

模型版本最小字段：`id`、`conversation_id`、`version_number`、`source_run_id`、`source_operation_id`、`source_task_id`、`operation_kind`、`parent_version_id`、`context_reference_id`、`path`、`sha256`、`format`、`bytes`、`report_ref`、`created_at`、`provenance_status`。会话编号只用于展示，父 ID 表达来源，禁止按编号相邻推断。

- 生成 v1；对 v1 减面得到 v2；再从 v1 减面得到 v3，v3.parent 仍为 v1。
- 只用旧描述重新文本生成时，记录 `context_reference_id`，`parent_version_id` 留空，动作明确为 regenerate；不虚构模型文件被供应商消费。
- 无输出文件的失败只有操作记录。有文件但检查不通过可以保存为失败候选，显示原技术状态；不能自动取代最近合格交付。文件无效或丢失时不可作为减面输入。
- 已有输入满足本次技术目标时，通过 assessment 解释“无需加工”，不重复提交、不创建内容相同的新版本，也不声称已生产。
- 文件按来源操作固定路径原子写入；随后在一个事务内提交本 Run Artifact、版本索引、父关系、实际报告及相关事件。按操作唯一约束拒绝重复登记，恢复同一操作不消耗新版本号。
- 前端预览选择、输入框引用、Run 实际输入、正式交付选择是四种不同状态。提交消息时冻结明确引用；预览其他版本及后台更新不能改变它。

第一阶段不创建额外全局 Asset 库，Conversation 本身提供资产范围；此后加入绑定/动画，可增加操作及产物类型和相应检查器，沿用版本及执行关系。新能力仍须独立接入，不能把当前 GLB 技术检查泛化为绑定/动画验收。

### D5. 用保存的 GLB 准备供应商输入，不依赖旧签名 URL

2026-09-13 查阅官方资料：减面接口支持任务引用、文件 token 或可访问 URL；文件 API 支持上传模型，返回 token。任务生命周期包含输出过期情形。这些是文档证据，本提案没有做真实上传或生产验证。

- [减面输入](https://developers.tripo3d.ai/en/docs/mesh-decimate)
- [文件上传](https://developers.tripo3d.ai/en/docs/files)
- [任务生命周期](https://developers.tripo3d.ai/en/docs/task-lifecycle)

v3 后续减面统一读取本应用保存的指定 GLB，核对会话归属、文件存在、摘要、结构有效性和供应商大小限制，内部调用 `POST /files` 获取 token，随后作为减面的 `input`。这条内部适配不接受用户文件路径、公开 URL、TaskID 或 token，也不开放模型导入入口。优先选择实际文件上传而非任意上一任务 ID，是为了让再次减面后的版本也具有确定输入，不假设所有加工任务 ID 都能被下一个 API 直接引用。

恢复点只冻结语义输入 `version_id + sha256 + operation_kind + parameters`。文件 token 等传输引用作为 `PreparedInput` 单独保存，关联 Run/Operation/version/hash；取得 token 不改变冻结语义参数和旧 profile 的恢复协议。每个新加工操作准备自己的引用；HTTP 操作有超时，上传最多三次尝试，尝试次数在发送前按操作持久化，重启不恢复额度，重试也检查停止/期限。上传不算模型生产提交，不重置 Run 预算；上传成功没有模型输出，不登记版本。

只有尚未发送生产 POST 的阶段允许重新准备文件 token。进入 `submitting` 前保存实际传输参数、生产扣额与绝对截止时间；之后不能因 token 错误、超时或响应丢失擅自改变 payload 并重发。已知 TaskID 续查，未知提交保留扣额并结束自动执行。停止后迟到上传结果不能再触发生产。

供应商输入失败应保留旧版本并解释，不能改成重新生成。真实验收需覆盖“生成后上传→减面”和“减面输出再次上传→再次减面”，不能只验证最初生成任务 ID 可被引用。

### D6. 独立聊天投影，HTTP 发命令，WebSocket 推送会话变化

新入口建议如下；路由名称属于设计选型，具体字段以实施时的接口类型和契约测试冻结。

| 入口 | 职责 |
| --- | --- |
| `POST /api/conversations` | 创建会话、首条消息和首 Run，带创建幂等键 |
| `GET /api/conversations` | 当前匿名访客的会话列表 |
| `GET /api/conversations/{id}` | 当前活动执行、版本概要、保留期与最近聊天快照 |
| `POST /api/conversations/{id}/messages` | 提交新消息或原问题答案；包含 client_message_id、可选版本引用、期望执行/问题身份 |
| `GET /api/conversations/{id}/messages?before=...` | 分页读取较早对话，默认 50 条、最多 100 条 |
| `POST /api/conversations/{id}/runs/{run}/stop` | 停止明确的 Run，禁止“停止当时碰巧最新的任务” |
| `POST /api/conversations/{id}/runs/{run}/retry` | 仅为 queue_full 的同一操作重试入队 |
| `GET /api/conversations/{id}/versions` | 当前会话版本列表，可分页 |
| `GET /api/conversations/{id}/versions/{version}/file` | 通过归属及会话有效期检查后预览/下载 |
| `GET /api/conversations/{id}/events?after=...` | 会话快照与新增事件下行 |
| `GET /api/conversations/{id}/trace` | 会话及逐 Run 的脱敏记录导出 |

发送载荷明确区分 `message` 与 `answer`。answer 必须携带服务器当前问题身份，不能仅靠页面上是否有问题判断；允许在回答选模问题时附带一个经校验的本会话版本。初次请求及新目标文字沿用现有输入长度边界，所有创建和引用校验在模型调用前完成。

消息投影分为 user、clarification、accepted_plan、operation_card、answer、run_result。问题只有 checkpoint 原子提交后发布；计划来自已接受 Intent；进度按 Operation 更新同一张卡；结束内容来自对应 Run 的正式结局。Eino History 不对外开放，完整 Agent 提议、Skill 加载和工具证据放在展开的执行记录中，来源及未核验标记保留。

v3 增加明确的 RunOutcome：`answer`、`delivery`、`ended`。answer 可以成功结束一次解释型交互，生产数为零，不沿用旧 `completed` 即技术交付的语义；需要新的版本化结果生成器/投影。delivery 只引用本 Run 真实输出与匹配报告；引用旧输入回答数据或无需加工使用 answer 与 assessment。自由回答保留 Agent 来源，事实卡片由 Go 渲染；程序不能保证自由建议每句话的语义。独立模型评测按 `technical-only-v1` 检查技术事实、已执行动作、预算和技术因果解释；外观符合性、材质配色、产物实际风格、部件、旧模型具体外形及未视觉检查声明均不评分。事实与原始文字的来源隔离仍保留，不增加结构化视觉解释契约作为验收前提。

原 `events.seq` 全表单调自增不重编号。会话流按绑定关系汇集所属 Run 事件并增加最少的会话事件，保证同一 `after` 可跨 Run 续读，允许序号有间隔。迁移期间先完成旧 Run 绑定再开放快照；新公开消息/版本与对应事件在同一事务提交。worker 退出后，清除匹配的活动指针与会话空闲事件一并持久化，前端依据会话可接受状态恢复发送，而非收到 stopped 就提前开放。投影消息有来源事件/操作唯一键，重连不会再次追加同一计划或结果。迟到事件保留其 Run 身份，不能更新当前 Run 卡片。

终态 Run 的核验可按不可变结果及事件水位缓存，当前 Run 按增量更新；不能每 500ms 重新装载整个长期会话全部 History。快照与游标一致读取，分页和 WS 可以重叠但客户端按身份去重。访客凭证、会话归属、同源/Origin、连接期间凭证失效和所有下载出口继续校验；不公开 token、源签名 URL 或本地路径。

前端维持 Go embed、原生 ES modules 和 model-viewer，拆分网络、连接、聊天及版本视图。左侧对话和底部输入，右侧预览及可折叠版本列表；较窄屏幕改为可切换区域。草稿按会话保留在当前页面的独立状态，切换回来仍在；本轮不承诺刷新后恢复未发送草稿，也不增加跨设备同步。等待澄清的回答草稿与执行忙碌时的新目标草稿分别存放。

### D7. 旧记录与旧协议采用增量包装

每个旧 Session 建立一个 Conversation 和首 Run 绑定。保留原 Run ID、checkpoint key/gob、History、预算、操作、文件路径、正式结果、Ended/Expires；不靠反序列化改写 Eino 的内部恢复字节。旧 `#session/{id}` 可解析到包装会话，新页面使用 `#conversation/{id}`。

旧 Artifact 依据持久化顺序分配展示版本号，保留原 Artifact/TaskID 映射；父关系只从明确可验证的操作证据获得，否则标记历史来源未知，不按数组顺序编造加工链。旧消息仅从 request、已生效澄清、答案、工具事实和正式结果构造；无法还原的历史正文不制造对话。

`/api/sessions/...` 继续作为旧单 Run 接口，返回原字段与结果语义，不能悄悄返回最新 Run；旧 `POST /api/sessions` 也原子创建包装会话和一个固定使用 v2 的兼容 Run。这是新创建使用 v3 的明确兼容例外：新 `POST /api/conversations` 的首 Run 及新消息入口创建的后续 Run 才使用 v3；已存在的 v1/v2 仍使用冻结 profile。公共访问和下载统一参考包装会话的有效期与归属，旧 Run.Expires 保留审计值，不再独立触发文件删除。

v3 在同会话内按不同 Run ID 隔离 checkpoint、问题、预算和恢复参数。Run 收尾事务同时保存正式结局、相应公开消息/事件和会话的到期候选；只有活动指针仍等于本 Run 时才能释放。服务启动先迁移、检查绑定与版本索引，再按原恢复规则核对每个非终态 Run，重建准确的活动指针；不能因指针缺失另建一个 Run。

替代方案“把所有旧 checkpoint 转为新键”没有业务收益且难证明正确；旧数据先删除再开始新会话也不满足历史版本和原任务保留要求。

### D8. 会话整体保留与清理

采用已确认的、可配置的 7 天窗口，避免连续会话默认无限占用模型存储。以下是本阶段的生命周期实现与验收规则；本提案本身不运行数据迁移或清理。

1. 活动 Run 存在时不得删除 Conversation、来源 Run 或任意历史版本。仍执行 Run 自己的生产前 24 小时空闲和生产后 30 分钟期限，不让“活动”无限阻止清理。
2. 最后一个 Run 结束且本地 worker 退出后，设置 Conversation.Expires 为该持久化 Ended 加 7 天。正常完成、纯回答、失败、用户停止和期限结束均适用。
3. 在到期前接受用户正式新消息时，原子创建新 Run 并保护整个会话数据；该 Run 结束后按新的 Ended 重新起算。澄清属于活动 Run，不另设会话窗口。只读访问、WebSocket 心跳、预览切换和未发送草稿不续期。
4. 迁移已结束旧 Session 时，Conversation 初始 Expires 精确保留其原期限。迁移或浏览不延期；只有用户明确继续才按第 3 条开始新的整体生命周期。原 Run.Ended/Expires 永远不改写。
5. 到期检查、接受新消息和进入清理互斥：到期后立即拒绝新请求及读访问；进入清理标记后不能接受或恢复新 Run。先阻断访问，再幂等清理会话涉及的所有 Run 模型目录、索引与记录；文件清理失败可重试，不留下可访问的半个会话。
6. 匿名 Cookie 的 30 天滑动有效期保持现行规则，它不延长会话数据期限；清除 Cookie 仍不能通过会话/版本 ID 找回访问权。

这替换“每条旧 Session.Ended+7天独立删目录”的执行方式。旧版本因后续明确创作而继续保留，是本阶段有意引入的行为变化，不应被误报为迁移篡改原终态。

### D9. 验收以连续创作行为与已有可靠性共同构成

主链使用一个明确静态资产目标，完成 v1；引用 v1 请求更低面数得到 v2；再次显式引用 v1 采用另一目标得到 v3；验证三次 Run、三个文件和真实父关系，刷新后能恢复对话和所有版本。受控文件必须让三次目标实际不同且具备可减面空间，不能用相同极小立方体伪装加工成功。

系统回归包括消息响应丢失/双标签并发、过期与发送竞争、输入版本串用、旧报告新目标、上传失败/迟到、生产未知、已知 TaskID 重启、文件落盘与版本登记强杀、停止后下一 Run 和旧回调、v1/v2 全协议升级。保留原 checkpoint 和结果 race/强制进程退出测试，针对新增事务边界扩充，不以正常 Close 代替崩溃。

浏览器验收覆盖首页、聊天澄清、草稿、版本引用、预览独立性、停止、重连、历史链接和窄屏。新增 Agent 连续创作案例集至少 8 类，每类 3 次：上下文承接、旧版引用、目标上限修改、纯解释、无需加工、能力越界、模糊指代、未知提交后续请求。使用真实 LLM 和固定 Provider，按 `technical-only-v1` 核对输入选择、动作选择、约束与非视觉解释；关键错误零容忍，其余适用项沿用至少 90% 标准。

真实 Tripo 验证单独记录生成→上传→减面→旧版本再次加工及费用/任务证据；不假定在线输出必定达标，失败须保留并分析。既定 20 场景 × 3 次基线评测仍是独立验收，不能用 8 类新测试代替。2026-09-14 按用户要求删除视觉相关语义评分及专用场景，`product` 的受众、技术目标与交付覆盖以及 `regenerate_reference` 的引用授权、文本重生成和版本来源覆盖继续保留；两组仍分别达到非视觉门槛。新 manifest 与语义审核明确相同的评分版本，旧证据和旧分数保留，不能混用新旧口径；范围调整不等同于新范围已通过。用户随后授权重新审核：在运行代码和 Skill 未变、案例输入和自动技术检查相同的前提下，允许复用完整第五批真实模型轨迹，在独立目录保存原始副本和新评分；必须重审所有提议、保留非视觉失败及原判分，不能仅删除错误标签自动计为通过。详见[评测范围](../../../../docs/evaluations/2026-09-14-technical-only-evaluation-scope.md)和[本次审核](../../../../docs/evaluations/2026-09-14-technical-only-reassessment-results.md)。方案阶段不调用真实生产、不执行任何迁移。

## Risks / Trade-offs

- [会话与原执行混用] → 保留物理执行身份，公共 Conversation 投影与旧 Runner 状态分开；新 Run 不复活旧终态。
- [新约束让旧报告失真] → 输入 assessment 与输出报告分开，逐 Run 冻结验收并保持历史结果不变。
- [模型选错旧版或文本重生成伪装加工] → 后端锁定引用、记录真实父关系与上下文参考，纳入 Agent 评测。
- [供应商引用失效或上传造成恢复歧义] → 采用本地不可变文件准备输入，语义身份与 token 分离；进入生产提交未知后不自动重发。
- [连续会话增加存储与上下文成本] → D8 有限保留、消息分页和有界上下文；本次不承诺无界对话历史全部进入每次模型调用。
- [停止后远端仍运行] → 停止卡和正式结果持续说明本地语义；远端结果取回不通过本次版本功能隐式实现。
- [网页聊天让自由回答显得权威] → 证据卡和正式交付由 Go 生成，建议文字有来源；按当前范围独立评测非视觉技术解释，不承诺对任意自由文字进行完备语义核验。
- [多层改造扩大一次发布风险] → 按数据包装、版本和执行、接口、页面、回归的顺序实施；保留兼容适配，发布前完成迁移强杀与旧协议验证。

## Migration Plan

1. 按已确认的 D8 准备迁移；停止旧进程接纳请求，备份 SQLite 及全部模型目录。不得让新旧程序同时写同一数据目录。
2. 在事务中增加会话、Run 绑定、消息、版本与索引；包装旧记录，记录迁移版本。升级失败整体回滚，反复启动不得重复登记。
3. 核对旧文件、版本来源和 checkpoint 身份；不可证明的历史来源明确标记，个别失败隔离，存储不可用不开放服务。
4. 按旧 profile 对在途 Run 恢复；既有任务不重提。关联模型由 Conversation 整体清理，先关闭旧独立 Run 删除路径。
5. 开放兼容读取和新 API，再启用聊天页面与 v3 新 Run。运行主链、旧入口和故障回归，更新阶段文档与相关 ADR，保留原验证记录。
6. 只有在新版本尚未接纳用户消息、调用模型、准备外部输入或推进任何远端生产时，才可以恢复完整备份并回退旧程序。一旦产生新事实，停止新增执行、保留新数据库和模型，以前滚修复处理；禁止覆盖成旧快照造成 TaskID 或版本丢失。

`first-asset-demo` 的归档不包含在本迁移中。本变更完成后若处理旧变更，必须先对照现行聊天/会话规格，不能把历史一会话一请求或网页不变限制重新覆盖回来。
