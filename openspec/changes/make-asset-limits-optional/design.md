## Context

动机和范围见 proposal.md。当前依赖已核对：

| 位置 | 当前行为 | 本次必须处理的依赖 |
|---|---|---|
| `internal/app/types.go`、`agent.go` | 两项上限是整数，零值补为 5000 / 10485760，保存时要求正数 | 新版必须表达缺失、明确取消和正数，不能仅删默认赋值 |
| `conversation_intent.go`、`conversation_agent.go` | 空字段继承来源意图并再次补默认，按该上限重评输入 | 取消约束不能被继承逻辑补回，输入技术通过不等于无需减面 |
| `agent.go`、`recovery.go` | 正常生产和重建均比较目标面数与验收上限 | 正常与恢复使用同一版本化参数规则 |
| `internal/asset/check.go`、`results.go` | 三项检查默认都适用；报告一致性要求两个上限为正 | 引入可选比较与不适用状态，保留文件检查和实测证据 |
| `profiles.go`、`skills/v3/` | Prompt、Skill 字节哈希与恢复版本绑定，多处硬编码 v3 | 新建 v4，不原地改旧 Skill；保持聊天能力守卫 |
| `internal/tripo/client.go`、`asset/check.go` | 下载上限 150 MiB，accessor 累计展开预算 256 MiB | 继续作为系统资源保护，不能成为用户验收上限 |
| `internal/web/static/`、评测代码 | 空字段显示“未记录”；用例默认期待 5000 / 10 MiB | 最小语义展示及独立的新规则评测 |

本次是跨意图、检查、持久化和恢复的行为变更，不是两个常量的删除。ADR 0003、0012 的默认补全条款与新规则冲突；其余技术检查、不可变历史和恢复原则继续成立。

## Goals / Non-Goals

**Goals:**
- 可选约束在澄清、正式意图、生产、恢复、报告、历史引用和展示中语义一致。
- 实际技术数据始终有证据；没有上限不等于没有检查，没有绝对面数上限不等于没有减面目标。
- 只在执行版本边界上兼容历史，不引入通用策略引擎或供应商抽象平台。

**Non-Goals:**
- 不追求自动推导“最佳面数”，不改变现有生产参数范围，不新增质量评分或视觉评测。
- 不支持在一个已接受的 Run 中途修改约束，不增加配置面板，不自动重做历史任务。

## Decisions

### 1. 将工具输入操作与已接受的可选约束分开

新版工具为每个上限表达三态变更：`inherit`（未提供新要求）、`set`（设置正整数）、`clear`（用户明确不限制）。省略字段按 `inherit` 解释；`set` 必须携带正整数，零、负数、非整数、溢出或互相矛盾的模式和值均拒绝，不能用零或极大数模拟无限制。

已接受意图和公开报告仍使用 `max_triangles`、`max_bytes` 这两个可识别字段，但 v4 值为正整数或显式 `null`。工具输入的三态归一化后才保存正式意图。采用版本化工具/公开 DTO 保留旧协议：旧 v1/v2/v3 的整数输入、旧字段序列化和恢复消息不改写；内部可用可空整数表示上限，通过版本适配器形成检查输入，避免业务路径各自解释零值。

优先级：本次 `set` / `clear` > 明确引用版本中可承接的来源约束 > 未设置。新建生成没有来源，两个 `inherit` 得到两个 `null`；引用来源本来无上限，也继续为空。只移除某一个上限不影响另一个。未指定绝对面数的“再减一些”不是 `clear` 指令，应保留适用约束并同时表达减面动作目标。

为新版约束记录来源：本次用户输入、继承版本、明确取消或未设置，以及可追踪的消息/版本标识。对旧记录只能标为“继承的历史验收约束”，不能仅因为值为 5000 就认定是默认，更不能伪称用户亲口提出。历史实际存储的上限保守继承，用户可以在新 Run 明确取消；草案显示其来源和变更。Go 校验引用真实存在及来源关系，用户语义提取仍由 Agent 完成，并独立评测，不能声称来源引用等同于语义证明。

非数值 `constraints` 中若仍有与 `clear` 冲突的旧面数/体积条款，Agent 必须依据用户明确变更同步整理，保留其他约束；保存差异证据。不得让旧文本重新注入已取消的上限。正式接受后，上限及来源冻结，重启、纠偏、模型调用不能修改。

替代方案：用 0 表示无限制会与缺失、旧版补全混淆；只用 nullable 输入无法表达“继承”和“取消”的差异；为所有资产换成更大的默认值仍然把制作偏好变为强制要求，均不采用。

### 2. 三种限制分别负责不同事情

| 类型 | 保存及约束位置 | 新规则 |
|---|---|---|
| 用户验收上限 | 当前 Run 正式意图、产物报告快照 | 独立可选；有值才比较 |
| 生产参数 | 每次操作的参数和理由 | 目标面数仍须在现有 500–20000 范围；上限有值时目标不得超过它；空时不加人为验收上限 |
| 系统保护 | 下载器、解析器、预算与调度 | 保留现有 150 MiB 下载保护、256 MiB accessor 展开预算及运行预算 |

Agent 可以选择 5000 作为某次生成目标，但必须记录为制作选择，不能复制到用户验收上限。缺少目标参数的工具调用拒绝为参数不完整，不再通过 Intent 上限反向生成参数。贴图质量 `standard` 等生产默认不受本变更影响。上限大于 20000 并不非法，因为上限不是必须达到的目标；上限小于当前工具最低目标 500 时不得擅自放宽，须在澄清范围内解释不可执行或由用户明确调整。

资源保护触发必须给出对应的下载/解析限制原因和不可验证范围，不得记为“超过用户体积上限”，也不得当作产物本体必然损坏。保留既有错误终止和有限重试边界，不增加通过减面、删约束或无限重试绕过保护的路径。资源失败时没有完整文件，就不能把截断字节数记为实际文件大小。

### 3. 报告分清测量事实、上限比较与总体技术通过

v4 报告保持文件有效性、几何规模、文件体积三个检查项，面数和字节数仍独立采集：

| 项目 | 情况 | 状态 |
|---|---|---|
| 文件有效性 | 文件符合现有静态自包含非空 GLB 检查 | `passed`，否则按证据失败或无法验证 |
| 几何规模/文件体积比较 | 有上限且有可信测量 | `passed` / `failed` |
| 几何规模/文件体积比较 | 无上限且有可信测量 | `not_applicable`，详情显示实测值与“未设置验收上限” |
| 几何规模 | 文件无法可靠解析，无法测量 | `unverifiable`，优先于 `not_applicable` |

技术 `passed` = 文件有效，且所有存在的面数/体积上限均通过。两个上限都没有时，合法文件可以技术通过，但不能说“低于要求的上限”或“所有创作要求已验证”。不能把 `not_applicable` 作为未跑文件检查或所有错误通行的理由。

报告与正式意图的可空上限必须精确一致；丢失应该存在的值、零值、错误状态、伪造实测或版本不匹配不能通过报告一致性校验。提取统一的版本化检查判定，供检查器、输入评估、结果投影及一致性验证复用，避免四处产生不同的“通过”定义。保留旧报告校验分支，不重新算历史通过状态。

### 4. 减面成功不能仅由上限检查判断

当前 `input_assessment.Passed` 会让“只减面”直接回答无需加工。新版必须另判动作目标：

- 用户只要求“达到不超过 N 面”，输入已经不超过 N 且满足其他适用条件时，保留零生产回答。
- 用户明确要求“进一步减少面数”，即便输入已通过全部可选上限，也仍有未完成的动作目标。
- 该相对减面目标保存初始明确输入版本及其可信实测面数；每次工具目标必须小于本次加工输入实测值；交付还必须证明最终输出实际小于初始指定版本，而不能只相信请求参数。
- 对“降低到指定上限”同样检查操作效果和已接受目标；若实际输出没有减少且目标仍未满足，不能通过“文件有效”冒充成功。
- 目标面数不转换为新增验收上限。无需精确数字也可由 Agent 提出合法的操作目标和理由；没有合法降低空间时说明工具限制并零生产结束。

保存最小的减面目标模式（达到上限 / 进一步减少）及必要的输入证据，提供独立的目标满足判断供无需加工守卫、纠偏和交付复用；不把操作目标强塞进文件检查结论。历史输入评估通过、新候选技术通过与当前目标完成，必须分别判断。

### 5. v4 执行协议隔离新旧语义

新聊天入口和会话后续消息创建 `asset-agent-v4`；旧单请求 `POST /api/sessions` 继续 v2，是明确的兼容例外，不代表网页仍补默认。旧执行无论处于澄清、排队、生产或恢复阶段都使用原协议和约束；同会话允许历史 v3 和新 v4 共存。

新增 v4 Prompt、四份只读 Skill 和工具 DTO，不原地修改 v3 的内容哈希。把“具备连续创作能力”和“采用可选约束”作为有限版本属性分别判断，审计所有 `== ConversationPromptVersion` 的分支：输入绑定、上传准备、资产父关系、回答结局、操作守卫、恢复重建和事件投影均须覆盖 v4。

正常提交与 `seedProduction` 使用同一版本规则。v4 重建使用已保存空值、目标模式、生产参数及输入身份，不能在恢复时补 5000 / 10 MiB 或刷新预算；旧版序列化和恢复哈希保持原样。未知或矛盾版本继续失败关闭；已知任务仍可依原 Run 的约束确定性查询和检查，未知提交仍不重发。

替代方案：原地修改 v3 会使冻结的 Skill 哈希、工具 schema 和在途 checkpoint 失配；一次性清空旧上限会改变历史验收事实，均不采用。

### 6. 最小展示适配和分层验证

网页只适配数据语义：计划显示“未设置验收上限”，差异显示取消/继承，检查显示“不适用（未设置上限）”和实测值；不改首页定位、布局或新增配置表单。HTTP 快照、WS 补读、版本侧栏、正式结果和 JSON 导出采用同一按 Run 版本投影。历史缺失证据仍显示未知，不能一律翻译成没有上限。

测试矩阵包含四种上限组合、显式取消、历史继承、非法值、损坏文件、资源保护、生产目标范围、相对减面、持久化恢复与旧协议。现有 20+8 场景各三次的 84 次真实 LLM 固定供应商评测保留案例身份及双套独立门槛；按新版规则更新依赖旧默认的预期和 stub 产物，而非删除纠偏案例。另增加本变更缺失的语义案例（每个三次），与基线分开报告，关键错误零容忍、其他适用维度不低于 90%。仅评测非视觉行为。

“超过默认值必须纠偏”改成“超过用户明确限制必须纠偏”；另外验证无上限的 6000 面、12 MiB 合法产物可交付且不自动纠偏。不得把全部约束检查设为不适用来提高分数。保留原始模型提议，伪造用户数值、取消明确约束和虚构技术达标仍属于错误。受控回归、Agent 评测、真实 Tripo 文件链路的证据分别存档，旧评测结果不替代 v4 证据。

## Risks / Trade-offs

- 无约束时模型可能更大 → 保留下载、解析、并发保护，公开实际指标；不承诺任意大小可处理，不新增隐含验收限制。
- Agent 把生产选择写成用户上限 → 分离工具字段和 Skill，记录来源及原始提议，以非视觉语义评测检出；Go 不宣称理解了用户自然语言。
- 兼容层增加代码 → 限定为有限协议适配，复用明确的领域判定，旧版快照/恢复回归防止语义漂移。
- 旧默认可能通过引用继承 → 明确标为历史约束并允许在新目标显式取消，不猜测或删除历史事实。
- 只移除数字导致减面提前结束或放行无效报告 → 相对目标与技术报告分开判断，并用跨生产/恢复/交付的测试验证。

## Migration Plan

1. 先落地版本化类型、可空检查与旧版适配，再接入 v4 工具、恢复、投影及 Skill，最后切换新聊天入口。部署前完成旧协议和新规则回归。
2. 部署前备份 SQLite 与本地资产目录；不批量修改旧 Intent、报告、Skill 哈希、事件或 checkpoint，不把旧上限自动转为空。
3. 采用明确版本的新增数据，旧会话后续目标自然使用 v4，历史数据按旧解释读取。恢复测试覆盖混合版本与已知任务检查。
4. 使用新版固定供应商完成完整非视觉评测；真实 Tripo 做无上限生成及一次同会话减面的有界冒烟，保存真实报告。若凭证或额度不可用，明确记录未验证，不以 stub 替代。
5. 回退不能用旧二进制直接处理已产生的 v4 执行；停止接受新目标并在支持 v4 的版本中排空或明确停止活动执行，再使用兼容修复版回退。只有未产生新数据时可直接回退，或在明确接受丢弃升级后数据的独立授权下恢复整套备份，不能自动删除数据。
6. 实施完成后更新当前文档和后继 ADR，说明新聊天规则与旧入口兼容例外；历史归档与旧验证报告不重写。按 OpenSpec 流程验证并在后续归档时同步主规格。
