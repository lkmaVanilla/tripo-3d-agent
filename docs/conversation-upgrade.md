# 聊天资产工作台升级与回退

适用于 `add-conversational-asset-workspace`。旧 Session 保留为旧执行，新增 Conversation 包装、消息与版本投影；旧 v1/v2 执行沿用冻结协议，新聊天执行使用 v3。升级不会把旧 checkpoint 改成 v3，也不会因为迁移重新提交已知 Tripo 任务。

## 停写并备份完整数据

1. 记录旧程序版本、配置和数据目录的**实际绝对路径**。默认配置是 `./data`，因此还要记录原启动工作目录；本地模型路径可能保存在旧 Session 中，恢复后必须解析到相同位置。
2. 停止入口接纳请求，向旧进程发正常终止信号，等待 HTTP、Runner 和 SQLite 全部关闭。确认没有其他服务、测试或旧进程仍写同一数据目录。新旧程序不得同时使用该目录；本项目没有支持多写实例的部署协议。
3. 在进程全部退出后复制**整个数据目录**，包括 `tripo.db`、存在的 `tripo.db-wal` / `tripo.db-shm` 和完整 `artifacts/`。模型一般位于 `artifacts/<run-id>/<operation-id>.glb`。只拷贝数据库，或在线直接复制单个 SQLite 主文件，都不是本方案的可恢复备份。
4. 保留备份不可修改，记录数据库与模型文件清单、字节数和 SHA256；保留原程序构建产物及恢复所需配置。数据库包含匿名归属凭证摘要和业务记录，备份按私有数据保存，不提交到仓库。密钥仍按现有配置保护，不写入验收报告。

## 独立副本先演练

运行仓库内的 [独立备份恢复演练](../internal/app/conversation_upgrade_test.go)：

```sh
go test -race ./internal/app -run '^TestConversationUpgradeBackupRestoreDrill$' -count=1 -v
```

该测试使用 `t.TempDir()`，构造真实 v1 Eino 暂停 checkpoint、旧产物和匿名下载归属，移除新会话表得到迁移前副本。关闭连接后复制 SQLite 与模型目录；仅调用 `New/OpenStore` 迁移，在核对后整目录恢复到**相同原绝对路径**。随后验证旧 Session/checkpoint 字节一致、两种下载地址返回相同 GLB、原答案能让旧 v1 Runner 继续。

生产数据演练必须在隔离环境执行，禁止模型/供应商外连，禁止接纳用户消息，禁止启动清理或调度。若复制到另一台机器或容器，保持原绝对路径及工作目录映射。直接在另一个目录打开原备份会让旧 `Artifact.Path` 指向原文件，并不能证明副本的文件恢复成功。

测试不会运行旧发布二进制，它验证当前程序保留的 v1 兼容 Runner；旧二进制本身的部署兼容性应使用留存构建产物在隔离环境补验。原有 v1/v2 冻结协议与强制退出测试仍须通过，本演练不替代它们。

## 单进程升级与迁移核对

迁移由 `OpenStore` 在一个事务中创建和回填会话表，成功写入 `conversation_schema.version=1`；失败回滚整个会话迁移。重复启动不得重复包装或登记版本。

迁移后先核对：

- `PRAGMA integrity_check` 为 `ok`，`PRAGMA foreign_key_check` 无结果；迁移版本为 1。
- 每条旧 Session 恰好关联一个 Conversation/Run；旧 Session JSON、checkpoint 字节及 ReplaySeed 输入哈希未改写；WaitID、队列位置、预算、截止时间保持原值。
- 每个旧产物的文件路径、字节数和 SHA256 与备份清单相符；版本数量与可回填的旧产物匹配。历史来源不能证明时允许明确标记未知，不能伪造父版本关系；缺失文件不得显示为可加工。
- 使用原浏览器匿名身份访问旧下载地址及新增版本下载地址，校验返回 GLB 与备份一致；旧链接和 `#session/` 能打开包装会话。

**当前没有独立的迁移 CLI 或可暂停调度的正式发布开关。** `cmd/server` 在 `New` 后立即调用 `Start`，其恢复对账和调度可能在 HTTP 开放前推进旧执行。因此“网页还没有开放”并不等于“尚无新事实”。隔离演练通过后，正式单进程启动应按已经越过回退边界管理；不能把直接启动正式服务当作可随时恢复旧快照的预检。

正常开放后检查新消息、纯回答、明确引用历史版本、异步进度和下载。涉及真实模型或供应商的验收已经属于新执行；保存对应 Run、Operation、TaskID、输入准备和文件记录，后续故障以前滚修复处理。

## 回退条件与操作

仅当以下条件全部成立，才允许回到旧程序和整套备份：

1. 自备份后没有接受新请求、后续消息或澄清答案。
2. 没有调用模型、准备或上传外部输入、提交生产、查询或推进远端任务、下载登记新产物，也没有改变清理事实。
3. 能证明整个窗口处于隔离状态，例如只完成 `New/OpenStore` 迁移而未调用 `Start`；所有进程与连接现已关闭。
4. SQLite、模型目录、匿名归属数据与原程序/配置可以作为同一恢复点恢复到相同路径。

满足条件时，先保留失败升级后的整目录供诊断，再将完整备份放回原位置，并启动旧构建产物。不要只换旧二进制继续写升级后的数据库，不要只覆盖 `tripo.db` 留下另一时间点的模型文件，也不要手改 checkpoint 或生产计数。

**只要出现新消息或外部动作，或者无法排除外部动作，就禁止用旧快照覆盖当前数据。** 先停止新增请求和执行，保存当前 SQLite、模型、日志及供应商任务身份，再修复新版本并继续向前。即使供应商调用超时、本地没有记录 TaskID，也不能用旧快照抹去提交未知状态并重新发起生产。

这是一条发布操作约束，产品没有提供自动回退命令。测试中的差分审计仅验证演练不会在发现新事实后恢复旧快照；数据库没有新增事件不能单独证明外部没有执行。
