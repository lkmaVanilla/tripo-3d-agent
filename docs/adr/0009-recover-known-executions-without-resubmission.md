# 恢复已有请求，未知提交不自动重发

资产生产与用户澄清跨越浏览器连接和服务进程的生命周期。MVP 持久化请求状态、预算及必要的检查点，并在以下边界内恢复原有执行。

| 情况 | 恢复行为 |
|---|---|
| 浏览器刷新或 WebSocket 断线 | 后台任务继续执行；凭证仍有效时，重新连接后恢复展示进度与记录 |
| 服务重启，正在等待澄清回答 | 从已保存的检查点恢复，保留已确认需求与澄清轮数 |
| 服务重启，正在等待生产名额 | 保留原队列顺序，核对已有生产请求后继续调度；不因恢复重复入队 |
| 服务重启，未开始生产且已连续 24 小时无用户操作 | 记录终止，不再恢复澄清或启动生产 |
| 服务重启，已有 Tripo 任务 ID | 请求未终止且未到截止时间时，继续查询原任务、检查产物；调用额度允许时再进入后续决策 |
| 提交结果未知，无法确认任务是否创建 | 停止自动执行并解释原因，不自动重复提交；保留已占用的生产额度 |
| 请求已终止或恢复时已到截止时间 | 保留结果与记录，不自动恢复执行；到期请求记录超时终止 |

所有恢复均沿用原请求的约束、已消耗预算、模型调用计数、执行截止时间和执行记录，并继续归属原会话。重启不能重置限制，也不能把同一次请求变成一次新的生成。一个会话只承载一个资产请求，见 [ADR 0014](0014-anonymous-sessions-and-concurrent-access.md)；恢复规则仅适用于尚未终止的请求，停止规则见 [ADR 0013](0013-execution-limits-and-local-stop.md)。

后台执行恢复与浏览器访问恢复分别判断。浏览器访问必须持有有效的匿名凭证并通过会话归属校验；凭证丢失或过期不触发后台任务停止，也不代表数据已删除。首版不提供旧会话找回或跨设备恢复，见 [ADR 0015](0015-browser-held-anonymous-credentials.md)。

排队请求从持久化状态恢复，沿用入队顺序；已停止的排队请求不再启动。恢复时先核对已有生产请求，再调度等待请求，不能因进程重启而把仍在执行的请求当作空闲生产名额，见 [ADR 0016](0016-bounded-production-concurrency-and-queue.md)。

恢复还需核对生产前的无操作期限和数据保留期限；重启不能延长这些期限，也不能恢复已经终止或到期删除的会话，见 [ADR 0018](0018-anonymous-session-retention-and-expiry.md)。

这一选择让连接中断与已知任务的进程恢复具有明确行为，同时避免在外部提交结果不明时重复发起生产操作。代价是需要保存并核对业务状态与 Agent 检查点；状态存储采用 SQLite，模型文件保存到本地持久目录，见 [ADR 0010](0010-sqlite-and-local-artifacts.md)。
