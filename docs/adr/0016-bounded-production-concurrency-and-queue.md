# 限制生产并发，并按入队顺序启动等待请求

匿名会话需要并发使用，但应用必须有明确的生产容量和等待行为。首版采用有限生产并发和有长度上限的等待队列，由 Go 执行层管理。

| 项目 | 首版行为 |
|---|---|
| 生产并发 | 同时最多 3 个处于生产阶段的资产请求，覆盖生成、异步等待、下载、检查和纠偏 |
| 等待队列 | 最多 10 个请求，按入队顺序自动开始生产 |
| 队列已满 | 提示繁忙，保留需求，允许稍后重试入队 |
| 等待用户澄清、查看结果 | 不占生产名额 |
| 排队期间 | 不消耗生产提交额度，不启动 30 分钟执行计时 |

3 和 10 是可配置初值，接入时依据实际 Tripo 账号配额核对。生产名额持续覆盖当前请求的生产过程，完成或终止后释放；同一请求内的纠偏继续遵守原有预算。

队列状态、顺序及生产阶段状态保存到 SQLite。同一请求只允许一个有效队列条目，重复提交不能重复占用名额。用户停止排队请求后不再自动启动；队列已满的请求只有在重新成功入队后才进入调度。服务重启时先核对已有生产请求，再按原顺序调度等待请求，保留原有预算及截止时间。

尚未开始生产的会话连续 24 小时无用户操作后结束，适用于已入队或尚未成功入队的请求。到期请求不再参与调度，后台轮询和心跳不延长该期限，见 [ADR 0018](0018-anonymous-session-retention-and-expiry.md)。

这一选择让额外访客可以等待后自动执行，并避免全服务串行或无限接纳待生产请求。代价是必须持久化排队状态，处理并发领取、重复入队、停止和重启恢复；这些属于确定性业务执行，不交给 Agent 决定。

应用生产名额与 Tripo 远端任务并发分别核对。本地停止不证明远端已取消，已提交任务仍可能占用远端容量。Tripo 的任务并发按账号和任务类别限制，HTTP 请求速率另有限制，见 [官方限流与并发文档](https://developers.tripo3d.ai/en/docs/rate-limits)。应用名额不能保证外部服务一定受理；外部提交尝试仍按 [ADR 0006](0006-three-production-submissions-per-request.md) 消耗生产额度。
