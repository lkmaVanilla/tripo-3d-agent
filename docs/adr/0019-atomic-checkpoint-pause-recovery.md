# 暂停与检查点原子发布，未提交暂停按原提议重建

业务等待状态、Eino 检查点及额外 Ready 标记分开保存，会在进程退出后形成不可回答的等待，或让新状态恢复到旧暂停。采用“准备草案、原子提交”的恢复协议：只有检查点字节、暂停身份和代次、业务状态及事件共同提交成功，暂停才对外生效。此决策细化 [ADR 0009](0009-recover-known-executions-without-resubmission.md) 与 [ADR 0010](0010-sqlite-and-local-artifacts.md)，不改变请求预算和停止语义。

Eino v0.9.19 在 `CheckPointStore.Set` 提供编码结果，恢复后继续使用原根 key。应用保留其 opaque 字节，以会话 ID、逻辑暂停 ID、提交代次和摘要绑定当前业务事实，不解析框架私有 gob，也不再用 `CheckpointReady` 判断可恢复性。每个 Runner 调用共享一个暂停协调器，回调遵守进程互斥到 SQLite 事务的锁顺序；事务不跨越模型调用、供应商请求或文件写入。

单独合并事务仍不能恢复首次检查点保存前的退出。待提交草案因此保存有限重建材料：完整协议输入、已接受助手提议、工具调用身份及参数摘要。恢复仅返回该原提议，让真实 Eino Runner 重新建立同一个暂停；不调用模型重新决策，不触发生产，也不增加调用额度。提交后删除该材料，不发展为通用模型缓存或日志重放平台。用户答案按等待 ID 保留；上一生产操作及报告直到下一恢复点提交后才可被替换，实际预算始终读取最新记录。

旧检查点通过禁用模型和生产提交的兼容 Runner 校验公开工具中断身份，再重新保存。旧答案必须能与该工具调用唯一关联。无法证明的旧记录明确失败并保留证据；已有任务 ID 的请求即使检查点损坏，仍在原期限内执行确定性查询与技术检查。只有依赖已损坏旧检查点、又没有独立重建材料的兼容草案，才按恢复不可用处理；完整有效的新草案仍优先恢复。未知提交不重发，停止和到期不能被旧回调覆盖。

代价是每个暂停增加一次草案写入，并需要维护小型恢复协议及兼容测试。替代的 Ready 修补不能解决身份错配，仅加原子事务不能覆盖首次检查点之前的退出，手工构造框架检查点则引入私有格式耦合。验证与上线/回退边界见 [恢复专项验证记录](../checkpoint-recovery-verification.md)。
