# 升级与回退：可选技术验收上限

本变更沿用 SQLite 表结构，新增数据采用显式 `asset-agent-v4` 执行版本和 `optional-v1` 约束标记。v4 意图和报告的两个上限均必须出现：正整数表示要求，`null` 表示未设置。零、字段缺失和未知版本不是“无限制”。旧 JSON 保持原表示，原执行继续加载对应旧提示、工具及 Skill；不进行批量改写。

## 升级前

1. 排空应用正在执行的请求并停止旧进程，避免复制过程中数据库与模型文件不一致。不要把“停止本地执行”当作 Tripo 已取消。
2. 保留旧二进制、提交号和配置位置。在进程完全关闭后，完整复制实际 `DATA_DIR` 到独立备份目录，包括数据库、可能存在的 WAL/SHM、模型文件和匿名访问所需持久信息。备份目录不得覆盖运行目录。
3. 先在备份的另一份隔离副本上启动新二进制，使用独立监听端口。需要离线检查时不配置 API 密钥，不让副本与生产进程共同处理同一个在途付费任务。
4. 检查旧请求状态、预算、截止时间、旧技术报告、版本关系和可下载文件。不能只检查新服务启动成功。

## 升级后语义

- 新聊天及旧会话中的新目标采用 v4；已接受的 v1/v2/v3 Run 不升级。旧 `POST /api/sessions` 仍创建 v2。
- 引用旧版的正数约束时保守继承并标注历史来源；当前用户明确取消时，新 Run 保存空上限，旧版本不变。
- v4 的 `inherit / set / clear` 是工具输入，正式意图以正整数/空值及来源保存。取消时若旧文本存在硬约束，必须给出完整更新后的约束清单，不能隐式恢复已取消条款。
- 在途 v4 的恢复复用原参数、输入身份、约束、预算及截止时间；已知 Tripo 任务继续查询，提交结果未知仍禁止自动重发。

## 回退边界

旧二进制不认识 v4，不能直接指向包含 v4 数据的运行目录。需要回退时先停止新进程，完整保留升级后的目录，再将旧二进制指向升级前备份的独立副本。备份之后新增的会话、版本和事件不能由旧程序继续处理，但其原始数据必须保留，不能自动删除或改标为旧协议。若有新提交的远端任务，先核对其身份和状态，避免回退产生重复付费提交。

## 已验证与未执行

`TestOptionalReopenMixedRecords` 创建独立 SQLite 数据，保存真实 v3/v4 记录，关闭后复制数据库到另一临时目录，再打开副本，核对意图空值、执行版本、结束时间、过期时间及原文件未改变。现有 `TestConversationUpgradeBackupRestoreDrill` 和迁移/强制退出测试继续覆盖完整旧数据及文件保留。

本次只验证了隔离测试数据，没有迁移、重启或修改用户正在运行的真实数据目录。真实运行目录的升级和备份属于部署动作，尚未执行。
