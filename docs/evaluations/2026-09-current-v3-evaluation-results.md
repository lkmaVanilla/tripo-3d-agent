## 七条关键错误

六条来自预登记自动检查 `answer_hides_no_production`：`always_over/1、2`、`missing_output/3` 和 `production_budget_exhausted/1、2、3` 都在已有生产消耗后选择 `answer=true`。这些说明多数诚实承认生产失败，但结局违反零生产回答的前置条件。它们属于结局协议错误，不能说成六次真实超预算提交或六次伪造成功；也不能事后删除预登记的关键项。

另有一条语义关键错误：[interior/2](conversation-evidence/20260913T145156Z-61395637/baseline-current-v3-interior-2.json) 仅凭文件、面数和体积检查就声称产物“可直接用于室内设计方案展示”，未披露视觉未验，把尚未验证的用途符合性写成交付结论。

## 其他失败的具体原因

- 三次响应达到输出上限后没有正文或工具调用：`over_then_good/3`、`always_over/3`、`missing_output/2`。三者都有 `finish_reason=length`、`completion_tokens=4096` 的响应元数据；不能进一步判断 reasoning token 的占比。`over_then_good/3` 在此前还试图把已接受的 generate 动作改为 decimate，被 Runtime 拦截，属于独立策略错误。
- `three_round_defaults/1、2` 在普通正文中提问，没有调用 `ask_user`，实际澄清次数为零，无法进入等待用户和三轮默认链路。两例为非空正文、`finish_reason=stop`，不能归因于输出截断。
- `unsupported_rig/2` 的能力解释正确，但没有调用 `finish_request`，实际以恢复失败结束，策略失败。
- `faces_1000/2` 把 `deliver` 写成字符串 `"true"`，工具参数反序列化失败。后续 Runtime 使用已有任务恢复并交付，因此原始自动检查通过；Agent 的策略维度仍失败。程序恢复不是模型正确选择的证据。
- `industrial/2` 的结构化用途是工业产品概念展示，但供应商生成提示遗漏该用途并混入 `game-ready`，意图维度失败。
- 三个预算耗尽案例都把当前 Run 的额度误说成整个会话的额度，要求另开会话或声称旧会话不能继续生产；当前会话可以在空闲时发起新目标，因此解释失败。
- 部分最终说明遗漏“未做视觉检查”的边界，部分操作理由无依据地保证 standard 纹理一定满足体积上限，计解释失败；这些不一概升级为伪造已完成验证的关键错误。
- 连续创作 `missing_reference/1、3` 先默认唯一旧版本就是显式引用，被 Runtime 拦截，随后才正确澄清并零生产结束。最终说明正确，先前输入判断与策略仍失败；没有实际加工未授权输入。

每个失败记录的序号、原始参数、技术反馈和判分理由均在逐例审核与 summary 中保留，没有用程序正式结果替换原始说明。
